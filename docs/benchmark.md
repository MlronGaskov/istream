# Сравнительный пилот ISTREAM, polling и keyset/refetch

Дата: 15.11.2026. Код эксперимента: `103842481357f91956e7e4fbd8bb891921fbc38e`,
на основе main `74c4d4febd220f44cbd08a4e1ded43af3a766977`.
Обычные клиенты и сервер ISTREAM не изменены; измерители находятся только в `benchmarks/`.

## Методика

Все данные клиентам передаются по HTTP. Запрос: `active=true`, проекция
`id,name,score`, порядок `score DESC,id ASC`. Три фиксированных полуинтервала
определены ключами строк 101–201, 2001–2101, 7001–7101 начального набора;
верхняя граница исключена. Начально в каждом 100 строк. При изменениях
количество строк свободно меняется, ограничения top-N нет.

- **ISTREAM:** существующий `SparseClient` с начальной загрузкой заданных диапазонов
  и Watch по собственным appliedVersion. First(1) нужен только для contextId.
  Применены миграции 001–003; цена clock и журнала включена в запись.
- **Polling:** каждый диапазон целиком перечитывается одним HTTP-запросом.
- **Keyset/refetch:** каждый диапазон перечитывается страницами по 25 строк,
  курсор содержит полный последний ключ. Сервер удерживает одну read-only
  repeatable-read транзакцию на весь проход; клиент публикует новый диапазон
  только после последней страницы. Курсор привязан к снимку и границам;
  завершение/отмена освобождает соединение, забытый курсор истекает через 30 с.

Условия score в baseline сохраняют возможность индексного чтения и при generic plan.
Оба baseline используют таблицу и индекс из 001, **без clock, журнала и capture-триггеров**.
Полное чтение также выполняется в read-only repeatable-read. Три диапазона
могут временно иметь разные снимки; окончательная сверка требует общего состояния
после остановки записей. Запросы всех трёх диапазонов baseline запускаются
одновременно, страницы одного диапазона — последовательно. Период начала
повторного чтения — 250 мс; при превышении периода проходы не перекрываются.
ISTREAM проверяет журнал с существующим интервалом 250 мс.

Каждый прогон получает новую БД `istream_pilot_*` в отдельном PostgreSQL;
рабочие БД и volumes не используются. Начальные 10 000 строк: `score=100000-10*id`,
все active, имена детерминированы seed=42. Индекс одинаковый. До запуска клиента
выполняется VACUUM ANALYZE; подготовка и seed исключены из измерений.

Один клиент, один писатель. Прогрев без записи — 1 с; затем три фазы записи
по 2 с. Средняя фаза проходит при отключённом клиенте: чтение/Watch отменены,
состояние сохранено, после двух секунд клиент подключается снова. Варианты
запускаются последовательно, порядок циклически меняется между тремя повторами.
Профили: 2 и 40 нагрузочных транзакций/с, соответственно 12 и 240 за прогон.
Каждая содержит пять SQL-операций: name, перемещение score (в том числе между
наблюдаемыми диапазонами), переключение active, insert внутри диапазона, delete.
После каждой фазы выполняется ещё одна контрольная транзакция, меняющая name
в каждом из трёх диапазонов. Итого 15 или 243 транзакции. План и seed одинаковы
во всех вариантах и повторах; SHA-256 планов проверяет `summarize.py`.

**Свежесть:** после контрольного commit запись приостановлена. Измеряется время
от получения writer-ACK до совпадения всех диапазонов с независимым SQL-снимком;
для ISTREAM дополнительно проверяется общая appliedVersion. Это время догоняния,
а не задержка каждой промежуточной операции. Его определение одинаково для всех
вариантов. Recovery отсчитывается от запуска чтения/Watch после отключения до
такого же совпадения. Наблюдение состояния — раз в 1 мс. В raw сохранены также
время перед COMMIT и верхняя оценка интервала commit→совпадение; writer-ACK
является измеряемой оценкой commit, а не его точной серверной отметкой.
Повторное подключение baseline начинает проход сразу, без ожидания очередных 250 мс.

**Счётчики:** consumed bytes тел ответов, включая SSE framing, subscribed/progress
и JSON-курсоры; без запросов, HTTP headers, chunk framing, TCP/TLS и непрочитанного
буфера. Initial отделён от updates; warmup сохранён отдельно и исключён из таблиц.
Requests включают Watch и отмену scan; pages — только HTTP-страницы keyset.
Reloads — законченные повторные загрузки диапазона, не начальные снимки и не delta.
Writer tx/s = нагрузочные транзакции / суммарное время трёх двухсекундных фаз;
паузы догоняния и контрольные транзакции из этого знаменателя исключены.
Задержка записи — BEGIN→возврат COMMIT для всех транзакций, включая контрольные.

Ресурсы: CPU-секунды процесса HTTP-сервера и его peak RSS из `/proc`, WAL bytes
и разности счётчиков `pg_stat_database` PostgreSQL. WAL включает clock и журнал
ISTREAM. Начальная подготовка исключена; CPU сервера включает запуск, initial
и warmup. CPU процесса harness (клиент, писатель и oracle вместе) сохранён в raw.
CPU PostgreSQL отдельно не измеряется; cache hits/reads показывают обращения
к буферам, а не загрузку CPU. Диагностические SQL-сверки входят в счётчики БД
и одинаковы по методике для вариантов.

## Воспроизведение и среда

```bash
# Отдельная проверка существующих тестов, до измерений:

# Результаты обязательно вне репозитория:
export BENCH_OUTPUT=/tmp/istream-pilot-results
mkdir -p "$BENCH_OUTPUT"
export CODE_REV=$(git rev-parse HEAD)

  pilot pytest -q benchmarks/test_baselines.py
docker compose -p istream-pilot -f benchmarks/compose.yaml run --rm --build pilot
python3 benchmarks/summarize.py "$BENCH_OUTPUT"
```

На проверенном хосте автоматический пул Docker-подсетей исчерпан. Использовались
временные overrides вне репозитория: для существующих тестов проект
`istream-clean-transfer`, `-f compose.yaml -f /tmp/istream-clean-network.yaml`;
для benchmark `-f benchmarks/compose.yaml -f /tmp/istream-pilot-network.yaml`.
Benchmark-override задаёт свободную на этом хосте подсеть `10.254.237.0/24`;
её не следует копировать без проверки занятых сетей. Файлы overrides сохранены
с исходными результатами. В штатном benchmark Compose фиксированной подсети нет.

Среда: Python 3.12.16, PostgreSQL 17.9 (Debian 17.9-1.pgdg13+1),
aiohttp 3.14.5, asyncpg 0.32.0, pytest 9.2.0; Linux x86_64, ядро 6.11.0-29-generic.
PostgreSQL 17 работает с PGDATA в tmpfs; сервер и клиент в одном контейнере,
HTTP через loopback, БД — через Docker bridge. Полные freeze и идентификаторы
образов сохранены вне репозитория.

## Выводы и ограничения

В этих условиях ISTREAM сократил объём обновлений относительно polling примерно
на **97.3%** при 2 tx/s и **64.1%** при 40 tx/s. Этому сопутствуют
расходы записи clock/журнала: например, на частом профиле медиана WAL —
741 224 B против 204 448 B, среднее время транзакции — 2,381 ms против 1,934 ms.
Скорость писателя соответствует заданным 2/40 tx/s во всех вариантах; это
ограниченная интенсивность нагрузки, **не предел пропускной способности**.

Polling в этом пилоте имеет меньшую медиану времени догоняния и восстановления,
чем ISTREAM. Replay не даёт общего преимущества по времени: при частом профиле
догоняние после reconnect у ISTREAM около 20 ms, у polling — 5 ms.
Keyset обеспечивает тот же полный результат, но требует примерно четырёх страниц
на загрузку и больше HTTP-запросов; на диапазонах такого размера выигрыша
от постраничного повторного чтения не наблюдается. Начальные тела ответов у всех
вариантов близки по объёму. Поэтому результат — обмен трафика на расходы поддержки
изменений, а не безусловное превосходство ISTREAM.

Пилот короткий: три повтора, две online-контрольные точки на прогон, один клиент
и один писатель, маленькие диапазоны, данные в кэше, PGDATA в tmpfs. Все PG block
reads в итоговой таблице равны нулю. Контрольные пакеты могут попадать в удобную
или неудобную фазу 250-мс цикла: отдельные повторы baseline имеют catch-up около
130 ms вместо единиц ms. Медианы не описывают задержку произвольного изменения
или хвост распределения; редкий профиль содержит лишь 15 writer-образцов за повтор.

HTTP работает через loopback без TLS и сетевой задержки. CPU сервера включает
запуск и прогрев; близкие значения порядка 0,3 с не доказывают различие эффективности.
WAL измерен на уровне изолированного кластера и может включать фоновое обслуживание;
счётчики PostgreSQL включают диагностические чтения. Двухсекундный разрыв проверяет
replay при доступной истории, без истечения retention. Это небольшой сравнительный
пилот для указанных условий, а не полная оценка масштабируемости и всех нагрузок.
