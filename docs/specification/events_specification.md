# Спецификация событий, версий и восстановления

## Назначение

ISTREAM предназначен для синхронизации отдельных материализованных диапазонов упорядоченного результата запроса без необходимости поддерживать весь результат на клиенте.

В рассмотренных подходах не выявлен единый механизм, одновременно обеспечивающий частичную начальную загрузку, range-scoped delta, replay изменений и локальное восстановление диапазона при недоступной истории событий.

## Модель событий

Изменения результата запроса описываются четырьмя логическими операциями.

| Операция | Условие | Данные | Действие клиента |
|---|---|---|---|
| **insert** | Строка появилась в результате или вошла в диапазон | `id`, `newKey`, `row` | Добавить запись по `newKey` |
| **update** | Пользовательские значения изменились, но ключ порядка остался прежним | `id`, `key`, `row` | Обновить пользовательские значения |
| **delete** | Строка удалена, перестала удовлетворять запросу или вышла из диапазона | `id`, `oldKey` | Удалить запись по `oldKey` |
| **move** | Строка осталась в диапазоне, но изменила ключ порядка | `id`, `oldKey`, `newKey`, `row` | Удалить запись по старому ключу и добавить по новому |

Здесь `id` соответствует стабильному $rowId(r)$, `key`, `oldKey` и `newKey` - полному ключу порядка $K_Q(r)$ в соответствующем состоянии, а `row` содержит пользовательскую проекцию $\pi(r)$. Материализованная запись имеет вид $m=(p,k)$ из формальной модели; `id` является последним компонентом ключа и не требует отдельного поля в $m$.

`move` является логической операцией, а не обязательным типом события протокола. Она может передаваться как `delete(oldKey)` и `insert(newKey)` с одинаковым `rowId` в одной атомарной группе. Отдельный wire-тип `move` допускается как оптимизация.

Изменение `rowId` рассматривается как удаление одной логической строки и добавление другой.

## Версионирование

Каждой атомарно применяемой группе изменений соответствует отдельная логическая версия $v\in\mathcal V$. Версии групп строго возрастают; состояние $D_v$ включает все полностью применённые группы с версиями не больше $v$.

Для каждого сообщения `delta` определяется $version(e)=v$ - версия соответствующей атомарной группы. Сообщение `progress` отдельно передаёт watermark потока, а не версию изменения.

Все релевантные изменения одной атомарной группы передаются и применяются клиентом как единое целое.

Каждый материализованный фрагмент $f_i=(I_i,M_i,w_i)$ хранит собственный watermark $w_i$, до которого клиент полностью обработал релевантные изменения. В протоколе этому значению соответствует `appliedVersion`.

Разные фрагменты могут находиться на разных watermark. Поэтому глобальная уникальность `rowId` в произвольном состоянии клиента не требуется.

Повторно полученные группы `delta` с версиями не больше `appliedVersion` не применяются. `appliedVersion` продвигается только после полного применения соответствующих изменений или обработки подтверждения `progress`.

## Начальное получение диапазона

Клиент запрашивает выбранный диапазон $I$ результата запроса $Q$:

`FetchRange(Q, I)`

Сервер возвращает:

- `rows` - упорядоченную последовательность записей с пользовательской проекцией и полным ключом порядка;
- `asOfVersion = v` - версию согласованного серверного состояния;
- `actualRange = I` - фактический диапазон, совпадающий с запрошенным;
- `contextId` - идентификатор контекста запроса $Q$.

`rows` и `asOfVersion` относятся к одному согласованному снимку $D_v$. История изменений должна позволять продолжить синхронизацию с этой версии либо явно сообщить о её недоступности.

Полученные записи соответствуют эталонному результату $R(Q,I,v)$.

Клиент создаёт материализованный фрагмент $f_i=(I,M_i,v)$, где $M_i=R(Q,I,v)$.

Начальное получение одного диапазона не требует загрузки всего результата запроса или остальных диапазонов.

## Определение фактического диапазона

При непрерывной прокрутке клиент не всегда знает границы диапазона заранее. Поэтому, помимо `FetchRange(Q, I)`, протокол предусматривает операции определения диапазона по количеству записей:

- `FetchFirst(Q, n)` - получить первые `n` записей.
- `FetchAfter(Q, k, n)` - получить до `n` записей начиная с границы `k` включительно.
- `FetchBefore(Q, k, n)` - получить до `n` записей перед ключом `k`.
- `FetchAround(Q, k, nBefore, nAfter)` - получить до `nBefore` записей перед `k` и до `nAfter` записей начиная с `k` включительно.
- `Count(Q)` - получить общее количество записей результата запроса.

Операции `FetchFirst`, `FetchAfter`, `FetchBefore` и `FetchAround` возвращают:

`(rows, actualRange, asOfVersion, contextId)`

где:

- `rows` - все записи выбранного фактического диапазона;
- `actualRange` - определённый сервером интервал полного ключа порядка;
- `asOfVersion` - версия согласованного снимка данных;
- `contextId` - идентификатор контекста запроса $Q$.

Сервер определяет `actualRange` по согласованному состоянию данных на момент `asOfVersion`.

Границы диапазона определяются следующим образом:

- `FetchFirst(Q, n)` - нижняя граница равна $-\infty$, верхняя - ключу следующей записи после первых `n` записей либо $+\infty$, если такой записи нет.
- `FetchAfter(Q, k, n)` - нижняя граница равна `k`, верхняя - ключу следующей записи после первых `n` записей с ключами не меньше `k` либо $+\infty$.
- `FetchBefore(Q, k, n)` - верхняя граница равна `k`, нижняя - ключу первой из выбранных `n` записей перед `k` либо $-\infty$, если записей меньше `n`.
- `FetchAround(Q, k, nBefore, nAfter)` - нижняя граница равна ключу первой из выбранных `nBefore` записей перед `k` либо $-\infty$, если таких записей недостаточно. При `nBefore = 0` нижняя граница равна `k`. Верхняя граница равна ключу следующей записи после выбранных `nAfter` записей с ключами не меньше `k` либо $+\infty$, если следующей записи нет. При `nAfter = 0` верхняя граница равна `k`.

Во всех случаях возвращается полный результат выбранного диапазона:

$$
rows=R(Q,actualRange,asOfVersion).
$$

Параметры количества записей определяют только первоначальные границы. После создания диапазона количество записей внутри него может изменяться.

Для `FetchFirst`, `FetchAfter` и `FetchBefore` требуется `n > 0`. Для `FetchAround` значения `nBefore` и `nAfter` неотрицательны, причём хотя бы одно положительно.

Пустой результат не означает отсутствие наблюдаемого диапазона. Если сервер определил корректные границы `actualRange`, клиент может создать фрагмент с пустой последовательностью записей и открыть для него `Watch`.

Например, если `FetchFirst(Q, n)` выполняется для пустого результата запроса, сервер возвращает `rows = []` и `actualRange = [-∞, +∞)`. Такой диапазон остаётся наблюдаемым и позволяет получать будущие события `insert`.

Операция `Count(Q)` возвращает `(count, asOfVersion)`. Она не создаёт материализованный диапазон.

После получения `actualRange` клиент использует его как фиксированный диапазон для дальнейшей синхронизации.

## Идентификаторы контекста запроса и подписки

Для связи начальной загрузки и последующей подписки используется `contextId` - непрозрачный идентификатор контекста запроса, создаваемый сервером.

`contextId` однозначно связывается с запросом $Q$, включая его проекцию, фильтрацию и полный порядок сортировки. Пока контекст действителен, сервер не должен изменять соответствующий ему запрос.

Операции начальной загрузки возвращают `contextId` вместе с данными, фактическим диапазоном и версией снимка. Последующие операции могут использовать `contextId` вместо повторной передачи $Q$.

`rangeId` - транспортный идентификатор конкретной подписки `Watch`, назначаемый сервером при её создании. Он используется для сопоставления сообщений `delta`, `progress` и `history-expired` с подпиской.

`rangeId` не является частью математического определения диапазона $I$. Один и тот же диапазон может получить новый `rangeId` после повторного подключения.

При создании подписки сервер сообщает клиенту её `rangeId` до передачи изменений.

Если `contextId` больше недействителен, сервер явно сообщает об этом. Клиент повторно выполняет начальную загрузку с исходным запросом $Q$ и получает новый контекст.

## Переход от чтения к подписке (fetch → watch)

После начальной загрузки клиент открывает поток изменений, используя `contextId`, `actualRange` и `asOfVersion`, полученные в ответе операции загрузки:

`Watch(contextId, actualRange, afterVersion = asOfVersion)`

Сервер должен передать все релевантные изменения с версиями больше $v$, включая изменения, произошедшие между получением снимка `FetchRange` и открытием `Watch`.

Для этого используется журнал изменений, согласованный со шкалой версий снимков. Переход считается корректным, если сервер может воспроизвести все релевантные изменения после версии начального чтения.

Если необходимая история уже недоступна, сервер возвращает `history-expired`. Клиент повторно получает диапазон и открывает подписку с новой версии.

Таким образом, при успешном `Watch` изменения между начальным чтением и подпиской не теряются.

## Фиксированный диапазон ключей и динамическое окно по рангу

ISTREAM синхронизирует фиксированный диапазон полного ключа порядка $I=[K_{lo},K_{hi})_Q$, а не фиксированное количество записей.

Операции `FetchFirst`, `FetchAfter`, `FetchBefore` и `FetchAround` первоначально определяют `actualRange` по заданному количеству записей. После этого границы диапазона остаются неизменными на протяжении его синхронизации.

При добавлении, удалении или перемещении записей состав диапазона может изменяться. Количество записей внутри него может увеличиваться или уменьшаться. Сервер передаёт соответствующие изменения через `delta`, но не поддерживает автоматически исходное количество записей.

Видимое пользователю окно по рангу формируется клиентом поверх материализованных диапазонов. Для непрерывной прокрутки клиент может хранить запас записей до и после видимой области.

Когда пользователь приближается к границе материализованных данных или запаса становится недостаточно, клиент выполняет дополнительную загрузку.

Для расширения вправо клиент может вызвать `FetchAfter`, передав верхнюю границу последнего материализованного диапазона. Для расширения влево используется `FetchBefore` с нижней границей первого диапазона.

Новый `actualRange` не должен пересекаться с уже материализованными диапазонами. Если сервер возвращает пересекающийся диапазон, клиент не добавляет его как независимый фрагмент без предварительного согласования границ.

При необходимости замены диапазона клиент сначала получает новый согласованный снимок, открывает `Watch` с соответствующей `asOfVersion` и обеспечивает применение последующих изменений. Только после успешного перехода новый фрагмент заменяет старый.

Таким образом, расширение или замена диапазонов не должны нарушать инвариант непересечения и приводить к потере изменений между начальной загрузкой и подпиской.

Таким образом, фиксированный диапазон ключей и динамическое окно по рангу являются разными объектами: ISTREAM обеспечивает синхронизацию первого, а управление вторым остаётся задачей клиента.

## Range-scoped delta

Для каждого материализованного диапазона $I$ сервер формирует только изменения, влияющие на его содержимое.

При определении релевантности учитываются старое и новое состояния строки: строка принадлежит результату диапазона, если она удовлетворяет фильтру $\varphi$ и её ключ $K_Q$ принадлежит $I$.

| Положение до изменения | Положение после изменения | Изменение диапазона |
|---|---|---|
| Вне диапазона или отсутствует | Внутри диапазона | `insert` |
| Внутри диапазона | Вне диапазона или отсутствует | `delete` |
| Внутри диапазона | Внутри диапазона | `update` или `move`, если изменились видимые данные или ключ |
| Вне диапазона или отсутствует | Вне диапазона или отсутствует | Событие не передаётся |

Если ключ не изменился, передаётся `update` только при изменении пользовательской проекции. При изменении ключа передаётся `delete` + `insert` либо эквивалентный `move`. Если ни ключ, ни пользовательская проекция не изменились, событие для диапазона не требуется.

Изменения определяются по состоянию до и после **полного применения атомарной группы**, а не по её промежуточным операциям.

Сервер передаёт релевантные изменения одной версии для диапазона одной атомарной группой:

`delta(rangeId, version, operations)`

где:

- `rangeId` - транспортный идентификатор активной подписки `Watch`, назначенный сервером;
- `version` - версия атомарной группы;
- `operations` - все релевантные операции этой версии для диапазона.

Клиент применяет всю группу атомарно. При гарантированном порядке доставки и полном применении предшествующих групп он может продвинуть `appliedVersion` до `version` этой группы.

Сообщения `delta` передаются в порядке возрастания версий. Пропуски номеров версий допустимы, если соответствующие группы не затрагивают диапазон; прогресс по таким версиям подтверждается через `progress`.

В транспортной реализации `Watch` использует SSE (Server-Sent Events).

Клиент самостоятельно хранит `appliedVersion` для каждого материализованного фрагмента. Это последняя версия, до которой все релевантные изменения полностью применены к локальному состоянию.

При разрыве соединения клиент не должен использовать автоматически сохранённый браузером `Last-Event-ID` в качестве версии восстановления. Этот идентификатор может соответствовать последнему полученному событию, изменения которого ещё не были применены.

Для восстановления клиент создаёт новое соединение `Watch`, явно передавая собственную подтверждённую версию через `afterVersion`. Автоматическое переподключение `EventSource` не используется, если оно не гарантирует восстановление именно с `appliedVersion`.

## Stream watermark

Логическая версия `delta` и stream watermark являются разными понятиями.

**Stream watermark** $V$ для потока $S(Q,I,v_0)$ подтверждает, что переданы все релевантные изменения с версиями из интервала $(v_0,V]$.

Для префикса потока $P$ watermark задаётся функцией $wm_S(P)$ из формальной модели. Корректность такого подтверждения обеспечивается требованиями протокола, а не одной монотонностью функции.

Для явного подтверждения прогресса сервер отправляет сообщение:

`progress(rangeId, watermark = V)`

Оно следует после всех релевантных сообщений `delta` с версиями не больше $V$ и может отправляться даже при отсутствии изменений в диапазоне.

Клиент может установить `appliedVersion = V` только после обработки всех предшествующих сообщений. Само получение `progress` без применения изменений не означает достижения версии $V$.

Watermark относится к конкретному потоку диапазона. Разные фрагменты клиента могут иметь разные подтверждённые версии.

## Применение событий к материализованному фрагменту

Пусть задан поток диапазона $S=S(Q,I,v_0)$ и два его префикса $P_a,P_b\in Pref(S)$, $P_a\sqsubseteq P_b$.

Для материализованного фрагмента $f=(I,M,wm_S(P_a))$ операция применения приращения потока определяется как

$$
\mathrm{apply}(f,\Delta P_{a,b}) =
\left(I,M',\mathrm{wm}_S(P_b)\right)
$$

Здесь $M'$ - упорядоченная последовательность материализованных записей, полученная последовательной обработкой сообщений приращения $\Delta P_{a,b}$.

При обработке сообщения `delta(rangeId, version, operations)` клиент атомарно применяет все операции группы к $M$:

- `insert` - добавляет новую запись в соответствии с её полным ключом порядка;
- `update` - обновляет пользовательскую проекцию существующей записи;
- `delete` - удаляет запись по старому ключу;
- `move` - удаляет запись по старому ключу и добавляет её по новому ключу в рамках одной атомарной группы.

После применения группы записи сохраняют порядок $\prec_Q$ и принадлежат фиксированному диапазону $I$.

При обработке сообщения `progress(rangeId, watermark = V)` содержимое $M$ не меняется. Watermark фрагмента может быть продвинут до $V$ только после полной обработки всех предшествующих релевантных изменений с версиями не больше $V$.

Повторные группы изменений с уже применёнными версиями игнорируются. Операция `apply` предполагает корректное начальное состояние фрагмента, упорядоченную доставку и полноту релевантных изменений.

При выполнении этих условий полученная последовательность должна соответствовать эталонному результату:

$$
M'=R(Q,I,wm_S(P_b)).
$$

Это соответствие является требованием корректности, которое проверяется инвариантами, а не следует из одной только записи операции `apply`.

## Replay после разрыва

После потери соединения клиент сохраняет материализованные диапазоны и последние полностью обработанные версии `appliedVersion`.

Для восстановления фрагмента $f_i=(I_i,M_i,w_i)$ клиент открывает подписку:

`Watch(contextId, I_i, afterVersion = w_i)`

Если история доступна, сервер передаёт все релевантные изменения с версиями больше $w_i$ в порядке версий.

При использовании браузерного `EventSource` клиент должен контролировать повторное подключение самостоятельно: при обнаружении разрыва закрывать прежний `EventSource` через `close()` и создавать новый с параметром `afterVersion = appliedVersion`.

Сервер использует явно переданный `afterVersion` как курсор восстановления и не заменяет его значением заголовка `Last-Event-ID`.

Если сообщение было получено, но не применено до разрыва, повторная подписка должна обеспечить его доставку. Повторно доставленные и уже применённые группы изменений игнорируются.

Клиент:

1. применяет полученные группы изменений атомарно;
2. игнорирует группы с версиями не больше `appliedVersion`;
3. продвигает `appliedVersion` только после полного применения группы или обработки `progress`;
4. по `progress` подтверждает актуализацию фрагмента до указанного watermark.

Replay не требует повторного получения диапазона и не затрагивает остальные материализованные фрагменты.

## Недоступная история событий

История изменений хранится ограниченное время. Сервер определяет минимальную версию, начиная с которой возможно полное воспроизведение последующих изменений.

Если клиентская версия слишком старая для replay, сервер возвращает:

`history-expired(rangeId)`

В этом случае клиент:

1. прекращает подписку для соответствующего диапазона;
2. помечает его текущее состояние как требующее восстановления;
3. повторно получает только этот диапазон через `FetchRange(contextId, I_i)`;
4. атомарно заменяет старое содержимое новым результатом и принимает новый `asOfVersion`;
5. открывает `Watch` начиная с новой версии.

Если `contextId` недействителен, клиент повторно создаёт контекст по исходному запросу $Q$ и получает диапазон с новым `asOfVersion`.

Если история вновь недоступна при открытии подписки, процедура повторяется.

Остальные материализованные диапазоны сохраняют своё состояние и продолжают синхронизацию независимо.

## Нормализация и проверка

Для эталонной проверки используется операция $Normalize(C_Q,V)$, приводящая проверяемые фрагменты к общей версии $V$.

Для каждого фрагмента $f_i=(I_i,M_i,w_i)$ при $w_i\le V$:

- если replay доступен, применяются релевантные изменения из $(w_i,V]$, а их полнота подтверждается watermark не меньше $V$;
- если replay недоступен, повторно получается результат диапазона из согласованного состояния $D_V$;
- изменения с версиями больше $V$ не включаются в проверяемое состояние.

В процедуре barrier генератор изменений остановлен, начатые атомарные группы завершены, а серверная версия $V$ зафиксирована.

После нормализации каждый проверяемый фрагмент имеет вид $(I_i,M_i^V,V)$.

Корректность проверяется сравнением $M_i^V$ с $R(Q,I_i,V)$: совпадением идентификаторов, ключей, пользовательских значений и порядка, а также проверкой глобальной уникальности `rowId` и непересечения диапазонов.

В обычной работе нормализация всех фрагментов к одной версии не требуется.
